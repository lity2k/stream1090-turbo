# 改了什么，为什么有效

[English](optimization.md) | 简体中文

共改动 8 个文件；`main.cpp` 与 `src/` 未动。以下内容全部位于 `include/` 或
`presets/BenchPresets.hpp`。

完整 diff 见 `patches/0001-cortex-a7-neon-pipeline.patch`。

## 原始问题的形态

`stream1090` 不搜索前导码。它为每个流维持一个 112 位移位寄存器，并在每个位时钟上
校验 CRC，因此每个输入样本的工作量是固定的，与收到多少报文无关。在 `-s 2.56 -u 12`
下有 `NumStreams = 12` 路 12 MHz 并行比特流，即每秒 1200 万次移位寄存器更新，
每次包含一次 112 位移位、两次 CRC 折叠和一次下行格式判定。

上游实现是每流两个 `uint64_t`，再加一层 12 流的标量循环。在 Cortex-A7 上，
处理 10 s 的 IQ 需要约 15.9 s CPU 时间：解码器追不上接收设备。

相关硬件事实（均在目标板上实测）：

- Cortex-A7，4 核，1.296 GHz，每核 32 KB L1D，共享 256 KB L2。
- NEON 是 64 位数据通路版本：128 位 Q 操作按两个 64 位半宽发射，因此一条
  `vshlq` 需要 2 个周期而不是 1 个。即便如此，仍是标量宽度的 4 倍。
- 没有 ARMv8 CRC32 或 crypto 扩展，CRC 必须手工折叠。

## 1. NEON 移位寄存器

12 个流分成 3 组、每组 4 路。一个 lane 承载一个流：

| 向量 | 内容 |
|---|---|
| `w0` | 各流的 bit 31..0 |
| `w1` | bit 63..32 |
| `w2` | bit 95..64 |
| `w3` | bit 127..96 |

不再逐流移位两个 64 位半宽，而是整组一次移位：`w0` 移出的 `carry` 送入 `w1`，
依次类推。`vsliq_n_u32(carry, w, 1)` 用一条指令完成 `(w << 1) | carry`，
替代常规的 `shl` + `orr` 两条指令——窗口移位和 CRC 折叠都用它。

同一趟还计算：

- 两次 CRC 折叠（`crc_56`、`crc_112`），用 `veor` / `vshl` / `vor` 对多项式处理；
- 下行格式字段（`w3 >> 27`）；
- 该格式是否为本次构建支持的格式；
- 以及该流是否命中。

命中结果打包进一个 `uint64_t` 位掩码（每流一位）返回给调用方。正常调用时掩码为零，
调度器根本不会进入——这是常见路径，保持无分支很重要。

**代价是一个下午的 bug**：`vbsl`/`vand` 需要全 1 掩码，不是 0/1 值。第一版把
每 lane 的命中掩码构造成 `0/1`，然后直接当位掩码用，导致只有 lane 0 生效；
报文数从 256 掉到 26，而每个独立 lane 看状态仍是"命中"。修法是用
`vceqq_u32(x, one)` 转换成全 1 掩码。`docs/validation.zh-CN.md` 描述了现在守住这一点的
逐位精确测试。

## 2. 双线程流水线

输入侧与解调侧的工作在一个块边界上是独立的，因此拆到两个线程：

- **生产者** — 读 IQ、去直流、IQ 低通 FIR、取模（`sqrt`）、2.56 → 12 MHz 上采样；
- **消费者** — Manchester 比较与移位寄存器更新。

`BlockRing::m_fullBlocks` 改为 `std::atomic`，使环形缓冲可跨线程共享。生产者通过
`m_produced - m_consumed < NumFreeSampleBuffers` 限流，使用条件变量而不是自旋。

结果：在 NEON 移位器已就位的前提下，15.87 s → 9.13 s，有效并行度 1.57 核。
消费者是关键路径，再加线程也无益。

## 3. Manchester 比较融进移位更新

原始循环

```cpp
m_newBits[j] = m_demodPos[j] > m_demodPos[j + (NumStreams >> 1)];
```

GCC 不做向量化——每 12 个比特发出十二组标量 `ldr / cmp / ite / str`。现在比较直接
在向量寄存器内完成，对半符号偏移比较，结果直接喂给移位。`m_newBits` 临时数组
完全删除：比特不再落到内存。

## 4. 环形缓冲余量（正确性，不是速度）

`NumFreeSampleBuffers` 是 `NumSampleBuffers - 2`，不是 `- 1`。解调器会回看上
一个块内的置信度/RSSI/前导码数据（`lookBack` 最大 1524 个样本）。只留一个块的余量时，
写者会在消费者正在读取的时刻覆盖的正是这块区域——这种数据竞争只会表现为高负载下
偶发的错误解码。该问题在双线程初稿中存在，在采信任何基准数据之前已修掉。

## 5. 输入块大小

`DesiredInputBufferSize` 由 8192 → 1024，每次交接的块从 154 KB 降到 21 KB，
这才让生产者→消费者的交接进入缓存驻留状态。8.43 s → 7.25 s。降到 576（14 KB）
无可测变化。

编译期可覆盖：

```bash
-DSTREAM1090_INPUT_BUFFER_TARGET=1024
```

## 6. Preset 实例化

`-s` 与 `-u` 是模板参数；每个受支持的组合都是一份独立实例化，上游的
`DefaultPresets.hpp` 展开为 27 份。单个编译单元装下全部 27 份所需内存超过 512 MB
板子的能力——`cc1plus` 会被 OOM kill。`presets/BenchPresets.hpp` 只实例化一组，
即 2.56 → 12。

这是构建配置的选择，不是把采样率硬编码：算法本身全部以 `NumStreams` 为参数。
它同时也更快（代码 190 KB vs 722 KB，在本硬件上快 19%）。在内存足够的机器上，
切回 `DefaultPresets.hpp` 即可在一个二进制里得到上游全部组合。

## 7. 跨核预取（v1.0.3）

取模环形缓冲位于流水线边界靠生产者的一侧。它有 86 KB——超出 32 KB L1D——且其中
每一行都由另一个核写入，因此消费者每次访问都 L1 miss，顺序执行的 Cortex-A7 只能
空等共享的 256 KB L2 应答。以每秒约 100 万个位周期、每周期 6 个缓存行计，这段
延迟占消费者约 7.1 s 中的相当一部分。

解法是更早地加载，而不是更少地加载：`consumeOneBlock` 会对 Manchester/移位循环
即将触达的缓存行提前几个位周期发出预取（`pld`）。预取距离由
`include/Global.hpp` 的 `STREAM1090_PREFETCH_DIST` 控制。L2 延迟就此与已在流水
中的移位工作重叠，而不是使其停顿。

在同一会话内与前一构建的对照复跑背靠背测量：7.42 s → 7.28 s（−1.9%），
AVR 输出逐字节一致。

## 这不是什么

- 不是通用 ARM 提速。`-mcpu=cortex-a7` 与 128 位 NEON 的前提是显式的；代码在别处
  能编译，但调优不可迁移。
- 不是解码器改动。在所有测过的采集上，报文数、载荷字节数与 AVR md5 均与上游一致。
- 不是完成品。消费者仍有 21.7% 在 `dispatchHandled`、9.6% 在
  `handleExtSquitterLongMessage`；两者都检查过，在本 ISA 上没找到有收益的重构。
  v1.0.2 基准之后实测得到的一项收益——跨核预取（§7）——已包含在 v1.0.3 中。
  测过并否决的方向见 `docs/benchmarks.zh-CN.md` §5。
