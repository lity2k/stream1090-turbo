# 基准测试

[English](benchmarks.md) | 简体中文

以下所有数字都来自把同一份固定采集通过 stdin 重放，因此只测量解码器本身——
没有 USB、没有接收设备、也没有实机带来的调度抖动。使用两块相同的板子
（board A、board B），均为 4× Cortex-A7 @ 1.296 GHz / 512 MB RAM，
内核与工具链相同。

负载：`stream1090 -s 2.56 -u 12 -q`，输入为 10 s、51,200,000 字节的 uint8 IQ
采集（2.56 Msps）。

每次运行的方法：

```bash
tools/bench.sh <binary> capture.bin 1 /tmp/bench
```

该脚本把所有核钉在 `performance` 调频策略上，先做一次不计时的预热把文件页读入，
测一次纯管道基线，再对解码计时。每块板、每个二进制跑 3 次；表中给出全部三次及均值。

## 1. 基线 vs 本项目

| 板 | 上游 (s) | 均值 | 本项目 (s) | 均值 | 加速比 |
|---|---|---|---|---|---|
| A | 15.947 / 15.997 / 15.903 | 15.95 | 7.212 / 7.300 / 7.208 | 7.24 | **2.20×** |
| B | 15.985 / 15.996 / 15.909 | 15.96 | 7.257 / 7.257 / 7.247 | 7.25 | **2.20×** |

"上游"指用相同编译选项编译的同一源码版本——即 `UPSTREAM_COMMIT` 记录的
`mgrone/stream1090` 提交的构建产物，不是发行版预编译二进制。

纯管道基线：同样 51 MB 为 0.41–0.42 s，即 I/O 只占优化后运行时间的 2.6%，
从不构成瓶颈。

输出一致性：256 条报文、9154 字节 AVR、md5
`e7bc7960e32d93d094c413300cd1227e`——两个二进制在两块板上逐字节相同。

## 2. 时间花在哪

每一行是单独一次构建；差值是单项改动的独立贡献（同一采集、同一选项、board A）。

| 构建 | real (s) | 说明 |
|---|---|---|
| 上游 | 15.87 | 参考 |
| `-DSTREAM1090_NO_DEMOD` | 5.07 | 移除 Manchester + 移位 + 调度 |
| `-DSTREAM1090_NO_SQRT` | 15.08 | 取模改为 `I²+Q²` |
| NEON 移位寄存器 + 双线程 | 9.13 | 步骤 1 + 2 |
| … + Manchester 融入移位 | 8.43 | 步骤 3 + 4 |
| … + 输入块 8192 → 1024 | 7.25 | 步骤 5 |
| … + 输入块 1024 → 576 | 7.24 | 无进一步收益 |

两个结论决定了后续工作方向：

- 解调侧占原始运行时间的 68%（15.87 − 5.07 s）。任何不触及 `DemodCore` 的优化，
  整体收益上限为 1.5×。
- 去掉 `sqrt` 只省 0.8 s，因此取模阶段不值得向量化。

## 3. 输入块大小的影响

`DesiredInputBufferSize` 决定 `Sampler` 中的 `NumBlocks`，进而决定从生产者交给
解调线程的每个块大小。

| 字节 | real (s) | L1 压力 |
|---|---|---|
| 8192（154 KB 块） | 8.43 | 块装不进缓存，每次交接都 miss |
| 1024（21 KB 块） | **7.25** | 舒适驻留 |
| 576（14 KB 块） | 7.24 | 无收益，同步开销更大 |

收益不是来自更小的 I/O，而是跨线程边界的缓存局部性。1024 是甜点值；该值可在编译期
用 `-DSTREAM1090_INPUT_BUFFER_TARGET=` 覆盖。

## 4. 最终构建的 profile

`perf record -F 2000`，占 15.26 G 周期的比例，board A：

| 符号 | 占比 | 侧 |
|---|---|---|
| 解调线程 lambda（Manchester + 移位，已内联） | 26.3% | 消费者 |
| `DemodCore::dispatchHandled` | 21.7% | 消费者 |
| `SampleStream::read`（读 + FIR + 取模） | 19.4% | 生产者 |
| `SamplerFunc<16,75,72>::sample` | 14.4% | 生产者 |
| `handleExtSquitterLongMessage` | 9.6% | 消费者 |
| `handleDF11ShortMessage` | 2.6% | 消费者 |

消费者工作约占 7.25 s 墙钟中的 7.1 s，生产者约 4.0 s。两者并发执行，因此墙钟由
消费者决定。这就是为什么继续优化生产者侧不再改变总时间。

## 5. 试过并否决的方向

下列每一项都实现或测量过，随后放弃。记录在此以免重复走一遍。

| 方向 | 失败原因 |
|---|---|
| 调度放第三个线程 | 调度器会改写移位寄存器状态；移交需要为全部 12 流做快照（此速率下约 1.1 GB/s），超过省下的工作量。 |
| 12 流分到 2–3 个线程 | `phaseDupCheck` 将流顺序耦合在一起；同步开销大于并行收益。 |
| 两次 CRC 折进 64 位 lane | NEON 没有 64 位可变移位；模拟比两次 32 位折叠指令更多。 |
| NEON 上采样器（`SamplerFunc<16,75,72>`） | 占 14% 周期但在生产者侧，不是关键路径——墙钟零收益。 |
| `-ffast-math` + `sqrtf` 向量化 | 已启用；取模循环是内存受限，不是计算受限。 |
| 把 `-u` 降到 8 | 流数变少，但解码输出改变（225 vs 256 条报文）；不是可无缝替换的优化。 |
| 单一二进制含全部 preset（9 组合） | 本硬件慢 19%：代码 190 KB → 722 KB，消费者侧 I-cache 压力。 |

## 6. 交叉编译构建

在 x86_64 主机上用 `arm-linux-gnueabihf-g++-14`、相同选项构建，在 board A 上测量：

| 构建 | preset 数 | real (s) | 相对本机 |
|---|---|---|---|
| 本机 g++ 14.2 | 1 | 7.23 | — |
| 交叉 gcc 14.2 | 1 | 7.82 | +8% |
| 交叉 gcc 14.2 | 9 | 8.62 | +19% |
| 交叉 gcc 13.3 | 9 | 8.40 | +16% |

交叉构建的 *用户态* 时间更少但墙钟更长，指向消费者线程：其代码生成略差，而墙钟由
消费者决定。板子上原生编译仍是最快选项；当板子内存装不下编译器时，交叉编译是可行选择。
